# HTML-отчёт к артефакту Stage 1 (Data Preparation) — проверка и план

Задача из `task1_from_me/`: демо `make_report.py` строит `mne.Report` по
синтетическому n-back EEG и сохраняет `eeg_report_demo.html` (5 МБ, 9 секций).
Вопрос: реализуемо ли это у нас, кто сохраняет отчёт, и можно ли считать его
первым run-артефактом.

## 1. Реализуемо — да, целиком, без новых зависимостей

`mne.Report` — часть ядра MNE. Всё, что использует демо, уже стоит:

| Демо использует | У нас |
| --- | --- |
| `mne.Report` (`add_raw/events/ica/epochs/evokeds/figure/html/code/sys_info`) | `mne` в `pyproject.toml` |
| `mne_icalabel.label_components` | уже вызывается в `preparation.py`, Step 3 |
| `mne_features.extract_features` | `mne-features` в зависимостях |
| `matplotlib` (Agg) | в зависимостях |

Проверено запуском на реальной записи SAM-40 (12 каналов, 128 Гц) — все методы
`add_*` доступны, `add_ica` + ICLabel отрабатывает на нашем ICA-юните.

## 2. Что измерено — и почему это меняет дизайн

Замеры на нашем реальном сигнале (12 каналов, 128 Гц):

| Что | Размер HTML |
| --- | --- |
| пустой `Report` (встроенные JS/CSS — фиксированная плата на файл) | 951 КБ |
| `+ add_raw(psd=True)` на одну запись | +168 КБ |
| `+ add_ica(inst=...)` на один юнит (9 компонент, свойства) | +1023 КБ |
| `+ add_ica(inst=None)` — только топографии | +117 КБ |

Состав данных: `distinguishing` — 34 записи / 34 ICA-юнита;
`sam40` — 480 записей / 120 ICA-юнитов (4 задачи на юнит).

Отсюда прямой перенос демо «по секции на запись» даёт для SAM-40:
`120 × 1.0 МБ + 480 × 0.17 МБ ≈ 200 МБ` в одном HTML. Браузер такое не
откроет, и время сборки — минуты `add_ica` поверх и без того долгого Stage 1.

**Вывод: отчёт делится на два уровня.** Уровень «всегда» — таблицы и сводные
фигуры по всей когорте, единицы мегабайт. Уровень «по требованию» — визуальная
детализация для нескольких названных юнитов.

## 3. Главное: бóльшая часть отчёта у нас уже вычисляется — и уходит в stdout

`preparation.py` сегодня печатает `print`'ом ровно те факты, из которых состоит
осмысленный отчёт, и они пропадают вместе с консолью:

- распределение значений `exclude_session_values` и `kept N/M` (Step 2);
- `selected N of M recordings ... carrying [...]` (Step 2);
- `QC BAD_peak= BAD_flat= spans= amplitude= LOF= interpolated= LOF_scores=[...]`
  (Step 3, на запись);
- `ICLabel 0=brain(0.99), ... -> excluded [...]` (Step 3, на юнит);
- `epoch rejection by condition ...` (Step 3, на запись).

Поэтому изменение — не «прикрутить визуализацию», а **записывать вместо
печати**: те же факты собираются в списки словарей → `DataFrame` → секции
отчёта. Это не новый слой, а перенаправление существующего вывода.

## 4. Ответ на вопрос «кто сохраняет: preparation или run_experiment»

**Сохраняет preparation, внутрь артефакта кэша.** Не из вкуса, а потому что
иначе не работает:

`get_dataset_dir` — content-addressed кэш. При попадании в кэш он возвращает
путь, **ни одной записи не прочитав**: ни `raw`, ни ICA, ни ICLabel в этот
момент не существует. Значит `run_experiment.py` физически не может построить
отчёт по подготовке — у него на руках только `epochs-epo.fif`. Отчёт — свойство
**артефакта**, а не прогона: один артефакт переиспользуется десятками
экспериментов, и копия отчёта в каждой Hydra run dir была бы одним и тем же
файлом, размноженным по результатам.

Про идею «возвращать объект, а объект потом сохранять» — она верна наполовину,
и полезная половина такая:

- **неверно** отдавать `mne.Report` наружу: наружу его получит только «холодный»
  вызов, а «горячий» вернёт `None`, и вызывающему придётся ветвиться на случай,
  когда отчёта нет. Это ветвление на пустом месте;
- **верно** то, что внутри стадии копится объект. Им становится сам
  `mne.Report`, создаваемый в Step 0 и пополняемый по ходу Steps 2–3, плюс
  плоские списки записей (QC, ICLabel, окна). Сохраняется он в Step 4 —
  в staging-каталог, до атомарного `rename`. Тогда отчёт публикуется той же
  атомарной операцией, что и `epochs-epo.fif`: артефакт либо целиком есть, либо
  его нет, и полуготовый отчёт наружу не виден.

Итоговая раскладка артефакта:

```text
datasets/prepared_cache/<hash>/
  config.yaml          # есть сейчас
  epochs-epo.fif       # есть сейчас
  report.html          # новое: отчёт уровня «всегда»
  qc.parquet           # новое (опционально, см. §7): та же таблица машинно
```

Роль `run_experiment.py`: одна строка в лог с путём к `report.html` артефакта
(и то же — для source/target при трансфере). Ни копий, ни симлинков.

Считать ли это «первым run-артефактом» — да по смыслу (это первое, что
производит прогон, и первое, что стоит открыть), но по месту хранения он
принадлежит кэшу, а не `results/`, потому что переживает прогон.

## 5. Состав отчёта: секции демо → наши

Демо сделано под ERP-эксперимент; часть секций у нас не имеет смысла в лоб.

| Демо | У нас |
| --- | --- |
| 1. Сырые данные | **тир 2** (по юниту) |
| 2. События | **заменяем**: у нас условия — аннотации; вместо `add_events` таблица «условие × длительность × запись» по когорте |
| 3. После фильтрации | **тир 2**, рядом с сырыми, в паре before/after |
| 4. Таблица ICLabel | **берём как есть и расширяем на всю когорту** — дёшево (текст), и это прямое доказательство для ICA-ablation |
| 5. `add_ica` топографии | **тир 2** (1 МБ на юнит) |
| 6. Эпохи после очистки | **тир 1**, один `add_epochs` по финальному `epochs` артефакта |
| 7. `mne-features` мощность по диапазонам | **тир 1**, но по классам (имена классов берутся из `DATASET_MAPPING`, а не выдумываются) — это ровно те признаки, на которых учится logistic regression |
| 8. `add_code` | **берём**: исходник `preparation.py`, артефакт объясняет сам себя |
| 9. `add_sys_info` | **берём, и это важнее, чем кажется**: hash рецепта по правилу не видит ни код, ни версии библиотек (`datasets.md`), а версия MNE/ICLabel меняет выход. Отчёт — единственное место, где реально использованные версии окажутся записаны рядом с артефактом |
| — | **новое: воронка отбора** — discovered → прошло `exclude_session_values` → несёт нужные условия → ICA-юниты. Сейчас это два `print`'а |
| — | **новое: таблица QC по записям** — BAD_peak/BAD_flat, секунды span, amplitude-bads, LOF-bads и LOF-скоры, интерполированные каналы |
| — | **новое: отбраковка эпох** по записи и условию |
| — | **новое: состав окон** — класс × условие × субъект × сессия/run. Это же таблица, которую хочет статья |
| — | **новое: рецепт** — `config.yaml` артефакта как `add_code(language="yaml")` |

Тир 1 (всегда) — всё, что таблицы и сводные фигуры: оценочно 2–4 МБ.
Тир 2 (по требованию) — +~1.2 МБ на названный юнит.

## 6. Как выбирается тир 2

Нужна ручка в рецепте подготовки. Здесь есть развилка, и она не косметическая:

**всё, что входит в `cfg.preparation`, входит в hash артефакта.** Поставить
`report.detail_units` в `configs/preparation/` — значит получить полную
пересборку 184-мегабайтного артефакта из-за смены параметра картинки. Это прямо
противоречит смыслу content-addressed кэша.

Рекомендация: **ручка отчёта не входит в рецепт**. Варианты по возрастанию
цены:

1. **Фиксированная политика в коде, без ручки вообще** (рекомендую для первой
   итерации): тир 2 строится для первых N юнитов каждого датасета, N=2 в коде.
   Ноль конфигурационной поверхности, ноль риска для hash, и практический смысл
   («посмотреть глазами, что ICA делает») закрыт;
2. **Переменная окружения** (`PREP_REPORT_DETAIL=all|2|sub-01_run-01`), читаемая
   в Step 0. Не входит в hash по построению, но это ровно тот «флаг режима»,
   который `overview.md` не любит;
3. **Отдельный узел `cfg.report`** вне `cfg.preparation`, передаваемый в
   `get_dataset_dir` третьим аргументом. Честно, но добавляет аргумент во все
   6 мест вызова в `validation.py` ради картинок.

## 7. `qc.parquet` — предлагаю, но отдельным решением

Таблицы QC/ICLabel/состава окон внутри HTML — это картинка для человека. Те же
`DataFrame`, положенные рядом как `qc.parquet`, читаются `run_analysis.py` и
LaTeX-артефактами (сколько компонент исключено, сколько каналов
интерполировано — числа, которые в статью просятся). Стоит три строки, потому
что `DataFrame` уже собран для отчёта. Но это расширение контракта артефакта,
поэтому — отдельным «да/нет», а не молча внутри этой задачи.

## 8. Порядок работ

1. **Step 0**: создать `mne.Report(title=...)` и пустые списки записей
   (`qc_rows`, `iclabel_rows`). Ничего не проверять — Step 0 у нас только
   конструирует.
2. **Step 2**: воронку отбора и таблицу условий записывать в списки; два
   существующих `print` заменить на `report.add_html` с той же информацией
   (печать можно оставить — консоль в живом прогоне полезна).
3. **Step 3**: в цикле по юнитам — заполнять `qc_rows`/`iclabel_rows`;
   для юнитов из тира 2 добавлять `add_raw` (before/after) и `add_ica`.
4. **Step 4** (после `concatenate_epochs`): секции по всему артефакту —
   состав окон, `add_epochs`, полосовая мощность по классам, таблицы QC и
   ICLabel из накопленных списков, `add_code` (`preparation.py` + `config.yaml`),
   `add_sys_info`. Затем `report.save(staging / "report.html")` **до**
   `staging.rename(artifact_dir)`.
5. `run_experiment.py`: одна строка в `log.info` с путём к отчёту артефакта.

Новых модулей не заводим: код отчёта живёт в `preparation.py` рядом с шагами,
которые его наполняют (по `overview.md` длинная линейная стадия лучше пяти
файлов). Прирост — оценочно 80–120 строк.

## 9. Что решено и сделано

Реализовано в `python_project/src/preparation.py` по решениям ниже.

1. **`preparation_version` не бампаем** — отчёт не меняет `epochs-epo.fif`.
   Следствие: у существующих записей кэша отчёта не появится (попадание в кэш =
   записи не читаются). Бэкфилла нет.
2. **Тир 2 — вариант 1 из §6**: константа `REPORT_DETAIL_UNITS = 2` в коде,
   ручки нет, hash не затронут.
3. **`qc.parquet` не делаем** — контракт артефакта прежний
   (`config.yaml`, `epochs-epo.fif`, `report.html`).
4. **`print`'ы оставлены** — Step 3 падает посередине, отчёт виден только в конце.

Отклонение от плана в одном пункте: строку с путём к отчёту печатает сам
`preparation.py` (в «Prepared …» и в «Reusing …»), а не `run_experiment.py`.
Протоколы в `validation.py` возвращают `(epochs, groups, cv)` и путь к артефакту
наружу не отдают; чтобы получить его в runner'е, пришлось бы менять сигнатуру
всех шести протоколов ради строки лога.

### Замеры готового отчёта

Прогон на 4 записях `distinguishing` (2 ICA-юнита, оба попали в тир 2):
131 с, `report.html` — 4.7 МБ. Тяжёлые секции на полном артефакте
(6209 эпох): `add_epochs(psd=True)` — 60 с / 2.2 МБ,
`mne-features` — 23 с.
