## Makefile — пульт запуска для пользователя

Пользователь не открывает `.venv` и не набирает `uv run python scripts/...`
руками: его способ запустить что-либо — `make <цель>` из `python_project/`.
Команда запуска — тоже часть исследования. Набранная в терминале, она живёт до
закрытия сессии и не воспроизводится ни другим человеком, ни тем же человеком
через месяц; записанная в Makefile — лежит в git рядом с кодом, который её
обслуживает.

**Агента это не ограничивает.** Агент свободно запускает
`uv run python scripts/...` напрямую — для проверки изменения, отладки,
разового прогона с любыми overrides. Заводить ради этого цель не нужно:
временная проверка агента и постоянный пульт пользователя — разные вещи.

Правила:

- новый скрипт получает свою цель и строку в `.PHONY` — чтобы у пользователя
  был способ его запустить;
- в Makefile попадают **воспроизводимые прогоны**, которые пользователь будет
  повторять: стадии конвейера и осмысленные конфигурации эксперимента. Разовая
  отладочная команда туда не попадает;
- Makefile остаётся тонким: экспериментальная цель — один вызов `uv run python
  scripts/run_experiment.py +experiments=<preset>`. Логика, циклы, ветвления и
  перечисление overrides в Makefile не переезжают;
- цель — *ярлык запуска*, а не второй слой конфигурации. Значения по умолчанию и
  контракт runner'а живут в `configs/`, научные комбинации и experiment-планы — в
  `configs/experiments/`.

### Overrides живут в цели, а не в терминале и не в `ARGS=`

Прогон, который пользователь хочет иметь под рукой, оформляется именованным
scenario, decoder или корневым пресетом в `configs/experiments/`; Makefile
выбирает только `+experiments=<preset>`. Проброса overrides снаружи
(`make sweep ARGS=...`) нет: состав эксперимента обязан лежать в git, а не в
истории терминала.

**Запрет касается overrides, составляющих эксперимент.** Аргумент, адресующий
уже произведённый выход, под него не подпадает: он не меняет, что посчитано, —
см. «Адресация уже произведённого выхода».

### Одна цель `experiment`, выбор пресета — правкой Makefile

`configs/experiments/` — обычная Hydra config group внутри `configs/`, а не
отдельный search root: её опции выбираются `+experiments=<preset>` тем же
composition-механизмом, что и любую другую группу. Единственная цель
`experiment` запускает `uv run python scripts/run_experiment.py
+experiments=<preset>`; чтобы переключить прогон, пользователь меняет имя
пресета прямо в строке Makefile. Отдельных целей на каждый пресет или на
scenario/decoder по отдельности нет — это увеличило бы число целей без
выигрыша, раз выбор всё равно одна строка.

Корневые пресеты — файлы прямо в `configs/experiments/`:

| пресет | оси sweep |
| --- | --- |
| `scenario_decoder.yaml` | `experiments/scenario: glob(*)` × `experiments/decoder: glob(*)` |
| `baseline_logistic_regression.yaml` | два перечисленных scenario × `logistic_regression` |

Пресет задаёт `hydra.mode: MULTIRUN` — без него `sweeper.params` молча не
сработали бы при обычном запуске. Ad-hoc запуск без пресета остаётся обычным
одиночным прогоном.

**Группа scenario одна** — `experiments/scenario/`. Раньше их было две:
`scenario/` с транзитными композициями SAM-40 из трёх задач
(`*_stroop_arithmetic`, `*_arithmetic_mirror`, ...) и `scenario_maybe_new/` без
них. Победила вторая: её содержимое перенесли в `scenario/`, транзитные файлы и
пресет `scenario_decoder_maybe_new.yaml` удалили, а каталог прогона в
`results/` переименовали под победивший пресет. Имя `*_maybe_new` осталось
только внутри сохранённых `.hydra/`-файлов того прогона: это запись того, чем
job запускался, её править нельзя. Ничего из кода имён каталогов в `results/`
не читает — состав направлений берётся из сохранённых конфигов.

**Состав `scenario/` и что из него читает статья.** 16 scenario-файлов
× 5 decoder-опций = 80 execution job'ов, а научных направлений на декодер — 27:
5 baseline, 2 cross-subject (только полные композиции A и B: leave-one-subject-out
внутри одной SAM-40 задачи назвал бы сдвигом участников прогон, который заодно
сузил состав задач), 12 cross-task (все упорядоченные пары среди
Full B / Stroop / Arithmetic / Mirror) и 8 cross-dataset
(A ↔ каждая композиция B). Направлений больше, чем файлов, потому что transfer
job тестирует один обученный source на списке targets — см.
«Execution job и logical scenario result».

Состав ровно совпадает с тем, что отчитывает статья, но прошлые прогоны шире:
`results/scenario_decoder (2026-09-01 % 08-54-09)` содержит и
`cross_session_distinguishing`, и три per-task cross-subject направления —
их рецепты убрали из группы уже после прогона. **Статья их не отчитывает**:
`SCENARIO_ORDER` в `src/analysis.py` перечисляет 27 направлений, а
`article_scenario_results()` отбрасывает всё, чего в нём нет. Поэтому лишние
результаты в `results/` анализ не ломают, но и в таблицы не попадают; чтобы
вернуть направление, надо вернуть и файл в группу, и строку в
`SCENARIO_ORDER` вместе с шаблоном таблицы.

Протокол `configs/validation_strategy/cross_session.yaml` и
`validation.build_cross_session()` при этом остались: сейчас их не выбирает ни
один scenario-файл, и они держатся именно как готовый вход для такого возврата.

### Плоские группы и `glob(*)`

`experiments/decoder/` и `experiments/scenario/` — плоские директории без
вложенных подпапок. Это сознательный выбор: **Hydra
`glob(*)` не рекурсирует по подпапкам группы**, поэтому вложенные папки под
`scenario/` (когда-то были `distinguishing/`, `sam40/`, `transfer/` ради
навигации) вынуждали бы full-sweep пресеты перечислять каждый путь вручную — и
новый scenario-файл, забытый в списке, молча выпадал бы из sweep. Различие между
датасетом и направлением несёт имя файла (`sam40_arithmetic.yaml`,
`cross_dataset_from_sam40_stroop.yaml`, ...), а не каталог.

### Оси sweep — целые рецепты, а не отдельные поля

Зависимые оси не передаются BasicSweeper по отдельности. Пара «признаки ×
pipeline» является одной decoder option; source с составом и списком его targets
— одной scenario option. Поэтому Hydra перемножает только корректные целые
рецепты и не создаёт совпадающие transfer-пары или модели с чужим входом.

Scenario option (`# @package _global_`) композит preparation-стороны через
`/preparation@preparation.source` и `/preparation@preparation.targets.<name>`,
переключает `override /preparation: transfer` для transfer-сценариев **и сама
выбирает протокол** через `override /validation_strategy`. Протокол при этом
дополнительно отвергает чужой датасет до запуска (`overview.md`).

### Состав SAM-40 задаётся задачами

Поле `mne_bids_pipeline_config.task` в preparation source и каждом элементе
`preparation.targets` — источник истины для состава SAM-40. Список всегда
включает `relax`: это low-demand класс. Для Dataset A значение — строка
`attention`.

Корневой config выбирает одну preparation-option. Non-transfer scenario
оставляет её одной стороной; transfer scenario композит те же options в
`preparation.source` и именованный mapping `preparation.targets`. Отдельного
`cfg.dataset`, а также полей `recipe` и `overrides` нет. Validation-builder
получает готовый `preparation_config`, а `prepare_epochs()` — только
соответствующий `mne_bids_pipeline_config`. Все ключи сверяются с аннотациями
Pipeline, а YAML list/tuple приводятся по тем же аннотациям. Runner отдельную
функцию подготовки не вызывает.

## Устройство скрипта: линейный сценарий, а не набор функций

Требование «одна функция» сформулировано для experiment runner'а, но дух общий:
скрипт в `scripts/` — не место для технической обвязки. Разрастается — значит
логика уехала не туда.

Что делать вместо `_`-хелперов, которые в такой файл просятся (`_load_dataset`,
`_build_cv`, `_extract_features`, `_save_tables`):

- разделять шаги баннером-заголовком (`overview.md`), а не `def`. Каждый такой
  хелпер вызывался бы ровно один раз, из одного места, в фиксированном
  порядке — это не переиспользование, а оглавление, за которое платят прыжками
  по файлу и протаскиванием `cfg` через сигнатуры;
- различается научный сценарий — он живёт отдельной функцией в `src/` и
  выбирается из конфига; скрипт не ветвится по имени стратегии;
- кусок действительно переиспользуемый и научный по смыслу — ему место в `src/`
  по правилам `overview.md`.

Обёртки ingestion — тонкие, без Hydra: пути и вызовы функций из плоского `src/`.
Они **несимметричны намеренно**: наличие функции в `src/` не означает, что
датасет принят в состав, и обёртка зовёт только принятое (`datasets.md`).

## Раскладка `results/`

**Корнем результата владеет пресет, а не базовый конфиг и не Makefile.**
`configs/config.yaml` задаёт только нейтральный fallback для запуска без пресета
(`results/default_run (...)` для одиночного прогона, `results/default_sweep (...)`
для sweep) и `hydra.job.name: adhoc`. Каждый пресет переопределяет
`hydra.sweep.dir` своим именем с timestamp и `hydra.sweep.subdir` —
`${hydra:runtime.choices.experiments/<группа decoder>}/${hydra:runtime.choices.experiments/<группа scenario>}`,
то есть вложенностью `<decoder>/<scenario>` вместо плоского `override_dirname`.

Отсюда следствие: имя каталога выводится из выбора групп самой Hydra, поэтому
**метка прогона в командной строке не пишется**. Рукописная метка ничем не
проверяется и расходится с составом — её появление в цели или в overrides
считать регрессом. Читаемое имя состава собирает анализ из сохранённого
конфига.

### Execution job и logical scenario result — не одно и то же

Transfer-scenario держит один source и **список** targets: decoder обучается
один раз на каждом source-fold и проверяется на всех targets этого job'а. Число
job'ов от этого меньше числа научных направлений, и разложение обратно —
ответственность раннера, а не анализа.

- Non-transfer job пишет три parquet (`windows`, `folds`, `importances`) прямо в
  свой каталог.
- Transfer job пишет по одному самодостаточному результату на направление в
  `targets/<имя target-option>/`: те же три parquet плюс `scenario.yaml`. Имя
  листовой папки — это `preparation.name` целевой option (`sam40_arithmetic`,
  `sam40_all`, ...), выведенное имя, а не рукописная метка и не ключ кэша.
- `scenario.yaml` — не Hydra config, а компактная проекция одного направления:
  `validation_strategy.name`, `preparation.source`, `preparation.target`,
  `pipeline.name`. Анализ читает её вместо `.hydra/config.yaml` и не узнаёт,
  сколько направлений разделили один job.
- `target_index` живёт только внутри прогона (validation → runner): при записи
  колонка дропается, и `window_index` перенумеровывается внутри каждого
  направления.
- Hydra создаёт `.hydra/config.yaml` до входа в runner; после успешного fit
  runner пересохраняет его с `resolve=True`, чтобы зафиксировать в том числе
  входную частоту, которую узнал feature extractor.

HTML-отчёты MNE-BIDS-Pipeline включаются булевым флагом
`save_preparation_html_reports` в preparation-option и складываются самим
Pipeline рядом с его derivatives, а не в Hydra output.

## Адресация уже произведённого выхода

Скрипт анализа читает дерево `results/`, поэтому его вход — не эксперимент, а
каталог:

- **job-каталог определяется файлом, а не глубиной**: наличие сохранённого
  Hydra-конфига и есть определение job'а. Одиночный прогон, один sweep и
  составной sweep обрабатываются одним кодом, как и любая будущая раскладка.
  Свой собственный выход скрипт за вход не примет;
- **каталоги задаются переменными окружения** `ANALYSIS_INPUT_DIR` и
  `ANALYSIS_OUTPUT_DIR`, которые читает сам `scripts/run_analysis.py`; make
  кладёт переменные командной строки в окружение, пробрасывать их в рецепт не
  нужно. Без `ANALYSIS_INPUT_DIR` вход выбирается сам — это **самый свежий
  sweep** в `results/`, а «свежесть» читается из штампа `(%Y-%m-%d %% %H-%M-%S)`
  в имени каталога, а не из mtime: скопированный или заново тронутый каталог
  остаётся датирован тем прогоном, который в нём лежит. Разбирать конкретный
  старый прогон — задать `ANALYSIS_INPUT_DIR` явно. Выход по умолчанию
  по-прежнему зашит в скрипте;
- **выход анализа лежит вне `results/`** — по умолчанию `python_project/analysis/`,
  то есть провенанс держится только тем, каким был `ANALYSIS_INPUT_DIR`. Вложенные job-каталоги внутри входа анализируются по
  отдельности и друг другу не мешают;
- **падать громко нужно на прерванном прогоне**: job-каталог есть, а таблиц
  нет — значит, сравнение посчиталось бы по неполному набору. Пустой лист
  сравнений, наоборот, валиден: если job один, сравнивать не с чем.
